Data-Science Practice

To build a ML pipeline, we need to:

  • preprocess the data, perform feature engineering, train a model …
  • with multi-source input …
  • so we need to learn a state…
  • while we evaluate the predictive performance…
  • as we avoid data leakage…

How do we deal with all that?

Data Ops: a basic example

Declare the pipeline

data_path = skrub.var("data_path")
data = data_path.skb.apply_func(pd.read_csv)

hist = skrub.var("hist_path").skb.apply_func(pd.read_csv)

X = data.drop(...).skb.mark_as_X()
y = data["target"].skb.mark_as_y()

X_join = X.merge(hist, on="id", how="left")

pred = X_join.skb.apply(
    StandardScaler(), cols=s.numeric()

    LogisticRegression(), y=y

With Data Ops…

  • Cross-validate without data leaks: fit() on training and predict() on unseen data.
  • Perform problem-specific data processing and data wrangling with sample filtering, joins and aggregations, multiple inputs and dynamic arguments.
  • Tune the architecture of the pipeline with hyperparameter tuning and validation scores.
  • Replay on new inputs.
  • Inspect the pipeline step-by-step, read the source code that generates a model.

Act 2: Dataset and problem

What are we here for?

  • The dataset: World of Warcraft Avatar history Dataset 1
    • World of Warcraft is a subscription-based online videogame.
  • The problem: Some players eventually stop playing, and thus stop paying their subscription.
  • On a given month, we want to enact some kind of policy on players at risk to stop them from leaving.

Important

On month M, we want to predict will_churn for month M+1, based on features built on data up to month M-1.

will_churn is a boolean flag that is True if the player has not played on month M and on month M+1.

  • Our “unit of analysis” is a (player character, month) pair.

  1. Source

The game

  • World of Warcraft (WoW) is MMORPG released in 2004 by Blizzard Entertainment.
  • Players create character avatars to explore the open game world and perform various activities.
  • Players level up their characters to make them more powerful.

Caveats

  • While we are interested in players, we have information only about their avatars. A player may stop playing with an avatar, but keep paying the subscription.
  • As this is past data, we cannot actually evaluate the effectiveness of whatever measure we decide to implement, so we can only try to predict player behavior.

World of Warcraft Avatar history

  • 132k separate text files.
  • ~36M timestamped “character is active” lines (heartbeats).
  • Time range: 2005-12-31 / 2009-01-10.

Time-aware cross-validation

Time-aware cross-validation

  • Features and session aggregations must only use data available at scoring time
  • Off-the-shelf TimeSeriesSplit assumes folds of equal size
  • Here the number of (character, month) rows changes every month — folds are unbalanced by nature

Time-aware cross-validation

  • A splitter that uses custom dataframe logic is required to handle the situation.
  • Custom splitters can use custom dataframe logic to select the samples
class Splitter:
    def split(self, X, y=None):
        ...
        for split_point in ...:
            test_month = pl.Series([split_point]).dt.offset_by("1mo").first()
            train_idx = (
                X.with_row_index("idx")
                .filter(pl.col("month") <= split_point)["idx"]
            )
            test_idx = (
                X.with_row_index("idx")
                .filter(pl.col("month") == test_month)["idx"]
            )
  • Splitters plugged in skb.mark_as_X(cv=Splitter()) are honored by cross_validate, train_test_split, randomized search, and scoring

Feature engineering: defining sessions

We want to model player behavior by measuring statistics about playing sessions.

  • How many sessions does a player have in a month?
  • How long do the sessions last?
  • Does the player have a consistent schedule?

Feature engineering

  • Monthly aggregates
    • Statistics by class, overall playerbase…
  • Location-based features
    • Zone rarity, where players spend their time
  • Lagged features
  • skrub.TableVectorizer to encode

Model selection

  • First pass with LogisticRegression to decide the architecture of the pipeline
  • Second pass with HistGradientBoostingClassifier (HGBC)
  • Data Ops are used to tune hyperparameters and architectural decisions

Act 3: The implementation

What is this section for?

  • The implementation revealed a number of pain points that Data Ops simplified.
  • We focus on some of the main issues without discussing the entire implementation.

Pain point 1 - Data preparation is part of the pipeline 1/2

  • Data is not clean: heartbeats are in text files scattered over hundreds of folders rather than in a more manageable format.
  • Boilerplate code and pre-processing scripts are brittle and prone to errors.
  • Once transformations are learned, they need to be replayed on new data, including the pre-processing.

Pain point 1 - Data preparation is part of the pipeline 2/2

Building the pipeline

def make_data_op():
    raw_files = skrub.var("raw_files")
    historical_data = raw_files.skb.apply_func(load)

    user_month = historical_data.skb.apply_func(
        build_churn_dataset
    ).skb.set_name("query")
    
    X = user_month["char", "month"].skb.mark_as_X(Splitter())
    y = user_month["churn_next"].skb.mark_as_y()

    feature_table = historical_data.skb.apply_func(build_feature_table)
    all_features = X.skb.apply_func(add_features, feature_table)
    encoded = all_features.skb.apply(skrub.TableVectorizer())
    data_op = encoded.skb.apply(HGBC(), y=y)
    return data_op

Pain point 2 - Hyperparameter tuning 2/2

With Data Ops, you can define the search space with the estimator:

dim_reduction = X.skb.apply(
    skrub.choose_from(
        {
            "PCA": PCA(n_components=skrub.choose_int(10, 30)),
            "SelectKBest": SelectKBest(k=skrub.choose_int(10, 30))
        }, name="dim_reduction"
    )
)

Pain point 3 - Treating pipeline decisions like hyperparameters 1/3

  • Model choices are not limited to model hyperparameters:
    • session_gap` (30/45/60 min)
    • include location features?
    • which lags?
  • These are data pipeline decisions, with big performance and runtime impact
  • Pipeline decisions modify the pipeline itself, and regular hyperparameter tuning does not work

Pain point 3 - Treating pipeline decisions like hyperparameters 2/3

  • Replace any value with a choice:
X_enc = X.skb.apply_func(build_feature_table,
-    session_gap=30,
+    session_gap=skrub.choose_from([30, 45, 60]),
 )
  • Tune data pipeline decisions, not only hyperparameters
X_enc = X.skb.apply_func(build_feature_table,
+    insert_additional_features=skrub.choose_bool(),
 )

Pain point 3 - Treating pipeline decisions like hyperparameters 3/3

  • One call to skb.make_randomized_search(backend="optuna", ...) turns the whole DAG into a search
  • skrub integrates and calls Optuna directly
  • Then, use the Optuna dashboard(http://127.0.0.1:8080/dashboard/?studies_order_by=desc) to navigate the results

Pain point 4 - Debugging and inspecting a pipeline 1/2

  • Inspecting a regular pipeline is complex and requires programmatic access
  • The result of intermediate steps is hard to access without re-executing everything
  • Once deployed, it is hard to maintain a trained model (“why was this step needed?”, “where is the source code?”)

Pain point 4 - Debugging and inspecting a pipeline 2/2

Data Ops execution report

  • Data Ops reports provide rich information about each node
  • The source code used to generate the Data Op can be retrieved from it
  • When a preview or environment is provided, intermediate results can be shown

Pain point 5 — The Need for Caching 1/2

  • Parsing is a node of the plan, rather than a separate pre-processing step
  • Cross-validation re-evaluates the entire plan => parsing is repeated in each fold
  • We need to choose between keeping parsing in the pipeline and quick iteration

Important

This is exactly what we want caching for!

Pain point 5 — The Need for Caching 2/2

  • Data Ops can be cached!
  • Joblib caching can be used to save time across folds.
CACHE_DIR = Path(__file__).parent / ".skrub_cache"
skrub.set_config(cache=str(CACHE_DIR))
wall time parse_files calls
cache off ~75 min (extrapolated) 63
cache cold 289 s 1
cache warm 213 s 0

In this case, ~15x speedup.

Conclusions

Main takeaways

  • skrub is a cool package 😎
  • Pre-processing should not be seen as separate from building your predictive pipeline 🔧
  • Data Ops mitigate and address issues throughout the development of the pipeline 🚒
  • Good libraries and abstractions are even more important in the age of agents 🤖
